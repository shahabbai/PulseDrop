# Receiver hotspot transfers

PulseDrop can transfer files without a router, an existing Wi-Fi network, mobile data, or an internet connection. The receiver creates a Wi-Fi hotspot and the sender joins it. Both devices still need working Wi-Fi hardware and must stay nearby. This is a receiver-hosted access point, not the separate Wi-Fi Direct group-negotiation protocol.

**Local network remains the default.** Its discovery, pairing, file format, transfer queue, progress, cancellation, and Inbox behavior are unchanged. Hotspot mode sets up the network underneath the same HTTP/UDP protocol; it does not use a cloud relay or upload files to a server on the internet.

## Platform support

| Device | Create a hotspot inside PulseDrop | Join a receiver hotspot |
| --- | --- | --- |
| Android 8+ | Local-only hotspot, with system Wi-Fi permission and compatible hardware | Android 10+: in-app Wi-Fi list, QR scanning/image import, Connect with system approval, and Disconnect; older versions: system Wi-Fi settings |
| Ubuntu/Linux with NetworkManager | Supported when `nmcli`, access-point mode, DHCP sharing, and normal network permissions are available | In-app Wi-Fi list, QR scanning/image import, Connect and Disconnect |
| Windows 10 2004+ / Windows 11 | Native adaptive 5 GHz / 2.4 GHz Mobile hotspot when the OS grants tethering access and has a suitable sharing profile; guided system settings otherwise | In-app Wi-Fi list, QR scanning/image import, Connect and Disconnect using Native Wi-Fi APIs |
| macOS | No automatic creation; use another device as the hotspot host | In-app Wi-Fi list, QR scanning/image import, Connect and Disconnect using CoreWLAN |
| iOS (when an iOS build is available) | Manual Personal Hotspot only; may require a cellular plan | Settings → Wi-Fi; can join an offline Android/Linux receiver |

Android's public [local-only hotspot API](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot) explicitly creates a network without internet. [Android's network request API](https://developer.android.com/develop/connectivity/wifi/wifi-bootstrap) prompts the user before joining. Apple provides [no public API to enable Personal Hotspot](https://developer.apple.com/forums/thread/113933). Microsoft's [mobile hotspot sample](https://learn.microsoft.com/en-us/samples/microsoft/windows-universal-samples/mobilehotspot/) requires an internet connection to exercise hosting. Use Android or a compatible Linux receiver when neither device has an uplink.

The sender controls and QR workflow are shared across Android, Linux, Windows and macOS. Hotspot creation and permission prompts follow each OS’s public APIs and hardware support; those cannot be made identical. Windows/macOS runtime behavior still needs native CI builds and physical testing, as described below. iOS does not expose the same general-purpose Wi-Fi scanning APIs and is not included in this four-platform discovery change.

## Receive without a router

1. Open **Receive files → Hotspot**.
2. Read the connection notice, then choose **Create hotspot & receive**. Creating a hotspot can replace the receiver's current Wi-Fi connection. Android may request Nearby devices permission; Android 12 and earlier require precise Location permission and Location services for Wi-Fi setup.
3. Keep the receiver app open. Its **Scan to connect** QR is the primary action. The Wi-Fi name/password are available in a disclosure, and the usual address, port and pairing code remain below.
4. On the other device, open **Send files → Hotspot → Scan QR**. Point its camera at the receiver’s QR. Mobile scanning prefers the rear camera. PulseDrop fills the network name and password, stops the camera, and previews the network. Press **Connect** to switch Wi-Fi, then approve any system prompt. The receiver address, port and pairing code are also filled when available in the QR. Add files and send; no password or pairing-code typing is needed for that path.
5. Without a camera, choose **Choose QR image**, or select the receiver in the in-app nearby Wi-Fi list and enter/paste its password. **Refresh Wi-Fi** scans again. Android may require precise Location access and Location services for the Wi-Fi list; QR joining on Android 10+ uses Nearby devices or legacy Location permissions instead. macOS requires Location access for Wi-Fi names; Windows may require it too. Use the inline instructions and refresh after granting permission. System Wi-Fi settings remain a fallback. Stay connected if the OS reports **No internet**. For a Wi-Fi-only QR or manual join, use **I’ve connected · Find receiver** and enter the receiver’s pairing code. If discovery is filtered, use **Enter address manually**. Choose the hotspot address in **Advanced network details** on a receiver with multiple interfaces.
6. Cancel from either side as usual. After transfers finish, **Stop hotspot** releases the network while keeping the HTTP receiver available on the restored/local network. **Stop receiving** also releases a hotspot created by PulseDrop. Disconnect an Android sender with **Disconnect hotspot**.

An externally enabled system hotspot remains under the user's control: PulseDrop neither claims it created that network nor silently disables it. On platforms without in-app creation, use **System hotspot settings**, then **I’ve enabled it · Refresh addresses**. A device that cannot create a hotspot can still send to an offline Android/Linux receiver.

To offer the same QR experience for a system hotspot, expand **Share a system hotspot by QR** on Receive. Enter the WPA2 Wi-Fi name and password from Settings and choose **Show connection QR**. The existing receiver starts and the form clears its credentials. PulseDrop cannot verify or enable that external access point for you. **Hide connection QR** clears the shared credentials without disabling the system hotspot. Stop receiving also clears the QR; turn off the system hotspot in Settings when finished.

## Lifecycle and privacy

- Android uses OS-generated credentials and retains its `LocalOnlyHotspotReservation` until Stop or activity destruction. Late startup callbacks after cancellation close their reservation. Permission denial, failed setup, lost Wi-Fi, and timeout have explicit recovery messages. Credentials are never written to browser storage or discovery packets.
- Android 10+ joining uses a Wi-Fi network request with no internet requirement and binds PulseDrop to that network. Disconnect, OS loss, and activity destruction unregister the request and clear the binding, preventing later transfers from remaining pinned to a dead network. Joining needs WPA2 credentials (8–63 printable ASCII characters); other security types can use system Wi-Fi settings.
- Android scans use `WifiManager`, with a separate scan state and permission request so a denied scan does not destroy a receiver session. Precise Location remains required for scanning even on Android 13+; Nearby devices alone does not permit `startScan`/`getScanResults` ([Android permissions](https://developer.android.com/develop/connectivity/wifi/wifi-permissions)). Scans run only from the visible workflow, stop on leaving/backgrounding, and finish within a bounded timeout. Android can throttle scans; recent results or an actionable retry are used instead of scanning continuously. Selecting a network pins Android’s request to its BSSID. No coordinates are requested or uploaded.
- Linux uses [NetworkManager's `nmcli`](https://networkmanager.dev/docs/api/latest/nmcli.html), without a shell or elevation. A fresh password comes from `/dev/urandom`. The owned profile uses WPA2/RSN, IPv4 sharing/DHCP, and no autoconnect. Its actual IPv4 address is read from the adapter. Hotspot creation now prefers 5 GHz, with the bounded compatibility sequence described below. NetworkManager may share another available uplink, but file transfers do not require one.
- Linux removes only the profile it created. It attempts to restore the previous connection after stopping/failing activation, provided the user has not selected a different network. A cleanup/restoration failure leaves an actionable error and retry; a failed startup with failed rollback explains how to remove the PulseDrop profile manually. Normal app exit cleans up its owned hotspot. Forced process termination/power loss cannot run cleanup; remove a leftover PulseDrop profile in system settings if needed.
- Wi-Fi controls are locked during active transfers. Setup, stop, manual refresh and retry show inline status. Password inputs support paste and Show/Hide; controls retain keyboard support and use at least 48 px height for hotspot actions. The pairing code is distinct from the Wi-Fi password.
- Wi-Fi scanning lists beacon names and signal strength before connection. These names are not proof of a PulseDrop receiver. Choosing a row fills its SSID; Android/Linux/macOS also use its BSSID where available. Windows’s available-network API groups access points by SSID/security, so it does not invent a BSSID. A QR identifies the network shown on the other device. On Linux, a joined network uses an owned, non-autoconnecting WPA2 profile and gets the same disconnect/restoration behavior as a hosted network.
- Windows uses the [Native Wi-Fi API](https://learn.microsoft.com/en-us/windows/win32/api/_nwifi/). It joins with an in-memory temporary WPA2/AES profile in manual connection mode; no password file or saved auto-connect profile is created. Disconnect attempts to restore the previously selected saved profile. An unrelated network selected in Settings is preserved. Missing Wi-Fi hardware, WLAN AutoConfig, permission denial and failed association produce retry/settings guidance.
- macOS links a small CoreWLAN/CoreLocation adapter into the app, without a helper process or shell. [CoreWLAN](https://developer.apple.com/documentation/CoreWLAN) scans and associates to WPA2 networks; Location authorization is requested on the main thread to access Wi-Fi names, without starting coordinate updates. The bundle includes camera and Location purpose strings. Disconnect checks the active SSID/BSSID before releasing it and attempts to rejoin the prior network using its existing system credential. If restoration is unavailable, reconnect in Settings; PulseDrop never reads other networks’ passwords. Changes chosen manually in Settings take precedence.
- QR generation and decoding run entirely in the app, without an internet service. The standard `WIFI:` QR includes Wi-Fi credentials and optional versioned PulseDrop metadata. Only valid Wi-Fi credentials and private IPv4 receiver endpoints are accepted. The QR is cleared on stop. It is a credential: show it only to the device you intend to connect.
- The shared scanner requests video only after **Scan QR** is pressed. Android includes the camera runtime permission; macOS includes its camera purpose string; Windows uses the WebView/system camera prompt. Linux WebKit permits that short-lived video request only from the app origin. No microphone is requested. Camera tracks and the app’s scan grant are released after scan, Stop camera, timeout, leaving Send, or app backgrounding; a late camera result after cancellation is immediately closed. The OS may retain the user’s camera permission for future scans. Images and camera frames are processed locally. Camera failure has a QR-image/manual-entry fallback. QR libraries load only when needed.

Android generates the hotspot credentials in the supported public API flow. The Android 16 SDK exposes a configuration-start method but does not expose the SSID/password builder setters needed for a reliable custom-password flow. QR transfers those generated credentials to the other device without weakening the Wi-Fi password or publishing it in the hotspot name.

## Adaptive Linux hotspot and speed testing

Linux hotspot setup checks the adapter's reported 5 GHz capability. When the optional `iw` tool is available, it reads that adapter's channels and excludes disabled, no-initiate-radiation/passive, and radar/DFS channels. It does not change the regulatory domain or transmit power. On NetworkManager 1.50+ and a VHT-capable radio, setup first requests 80 MHz only when all four channels in a supported non-DFS block are permitted. If that setup fails, it tries conservative 5 GHz settings, then 2.4 GHz compatibility settings. Older NetworkManager versions skip the newer channel-width property. Without `iw`, NetworkManager chooses the 5 GHz channel and retains its regulatory checks; 2.4 GHz remains the setup fallback.

There are at most three setup attempts, using the same owned profile and credentials. A failed wider setup resets the channel width before retrying. Exhausted attempts remove the profile and attempt to restore the previous connection; a network selected manually during setup is preserved. A running hotspot is not switched between bands during transfers. A client that only supports 2.4 GHz will need a compatible system hotspot: automatic fallback handles host setup failures, not a phone's inability to see a successfully created 5 GHz network.

The existing Receive hotspot status shows the observed band, channel and width after activation, and explains a setup fallback. If the radio cannot be queried, the message explicitly distinguishes the configured band from unavailable actual channel details. Android hotspot creation and the transfer protocol are unchanged. Joined Linux, Windows and macOS sessions also show native connection-band details when available; this is a connection snapshot, not continuous radio telemetry. The `Power save: on` flag alone is not proof of AP sleeping; Linux's station power-save setter may be unsupported in AP mode.

To compare against the earlier channel-6/20-MHz test:

1. Close the previous PulseDrop process and run the new Ubuntu build. The Android app can stay on its existing version for this change.
2. Open **Receive files → Hotspot → Create hotspot & receive**. Check for **5 GHz · channel … · 80 MHz** in the status; a fallback will be stated. Setup can take longer if the driver rejects an attempt.
3. Connect the phone using the new QR, keep both devices close and both apps visible, and send the same large file. Record total elapsed time and average MB/s. Repeat in the reverse direction on the same hotspot without restarting it; verify the saved file's size or hash.
4. During each direction, capture the commands below twice, a few seconds apart. `station dump` reports Ubuntu's recent TX/RX radio rates; these are not file-transfer MB/s. Compare changes in retry and TCP out-of-order counters, rather than interpreting cumulative counts as a loss percentage.
5. Stop the hotspot and confirm the previous Wi-Fi connection returns. Repeat a regular LAN transfer to check for regressions.

```bash
iw dev wlo1 info
iw dev wlo1 station dump
ss -tin state established '( sport = :53612 or dport = :53612 )'
```

Substitute the actual adapter and receive port if different. `pacing_rate` on a mostly receiving TCP socket describes its outbound direction and is not the incoming file's throughput limit. Successful setup/build tests do not establish a speed increase; measure the actual PC/phone pair. If 5 GHz is selected but throughput remains poor, compare link rates and out-of-order/retry deltas before considering driver or transport changes.

Band and width settings follow [NetworkManager's wireless settings](https://networkmanager.dev/docs/api/latest/settings-802-11-wireless.html); explicit channel width requires [NetworkManager 1.50+](https://networkmanager.dev/docs/libnm/latest/NMSettingWireless.html).

The initial Linux adaptive-hotspot validation passed 51 Rust tests and 79 JavaScript tests, an Ubuntu DEB build, and a Windows native Wi-Fi cross-compilation check. A read-only probe of the test PC selected channel 36 at 80 MHz. NetworkManager's offline parser accepted wide 5 GHz, conservative 5 GHz, and automatic-channel compatibility profiles. Isolated native Linux app checks used simulated Wi-Fi tools and real HTTP receives to verify all three setup outcomes, exact saved bytes, radio status in both themes, narrow layouts, stop, and restoration. Those isolated checks did not activate a physical hotspot or measure throughput. The user subsequently confirmed that a real Ubuntu 5 GHz hotspot resolved the slow Android transfer.

## Windows adaptive hotspot and macOS joining (0.5.0)

Windows uses the public [Mobile hotspot configuration](https://learn.microsoft.com/en-us/uwp/api/windows.networking.networkoperators.networkoperatortetheringaccesspointconfiguration.band) and [tethering manager](https://learn.microsoft.com/en-us/uwp/api/windows.networking.networkoperators.networkoperatortetheringmanager.createfromconnectionprofile) APIs. The band API needs Windows 10 2004 or newer. PulseDrop checks availability before offering Create; Windows must expose an internet connection profile and grant Wi-Fi/tethering control. Hardware, OS permissions and policy may prevent native hosting. In that case use **System hotspot settings**, choose **Properties → Edit → Network band → 5 GHz** if available, and share the system hotspot by QR, or use an offline Android/Linux host.

When native creation is available, PulseDrop checks 5 GHz support, requests it first, and retries on 2.4 GHz for a band/radio restriction. Unsupported 5 GHz starts on 2.4 GHz immediately. General permission, sharing-profile and service errors fail without repeated network changes. Windows controls the channel and channel width; PulseDrop does not claim to force 80 MHz. Status explicitly says **Configured for 5 GHz** or **Configured for 2.4 GHz**, rather than presenting a requested band as a measured radio result.

PulseDrop refuses to replace an already active system hotspot. It saves the previous hotspot name, password, band and authentication in memory, uses fresh random WPA2 credentials, and restores previous settings on Stop or normal app exit only while the configuration is still its own. It respects a newer configuration selected in Settings. Bounded operations and a retained **Clean up setup** control allow cleanup after a setup timeout. Windows stores Mobile hotspot configuration itself; an app crash or forced termination can leave that temporary configuration in Settings, so use Stop before closing and check Settings after an interrupted session.

On **macOS**, use **Send files → Hotspot**, choose a receiver’s 5 GHz Wi-Fi or scan its QR, then Connect. macOS Location permission is still required to expose Wi-Fi names. CoreWLAN supplies the actual joined channel/band/width when available. Automatic hotspot creation is outside this macOS release; use Android, Linux or supported Windows as the host. The existing LAN Receive screen still works when a Mac joins that network.

For Windows hosting, PulseDrop compares local addresses before and after setup. A unique new private IPv4 address is used for pairing; if none can be identified unambiguously, the QR carries Wi-Fi credentials only. Join first, then use receiver discovery or the hotspot address in Advanced network details. A router/uplink address is never substituted into that native Windows host QR.

Windows joining uses the associated access point’s BSSID and center frequency for its band/channel readout. A missing or denied radio-details query does not fail an otherwise successful join. Normal Wi-Fi association negotiates the connection with the host; PulseDrop does not force client channel widths or change the OS’s regulatory settings.

## Validation and physical test checklist

Automated tests cover the existing transfer protocol and discovery plus hotspot credential validation, platform capability fallback, permission/connection errors, cancellation of pending setup, stale results, timeout cleanup, UI field focus, credential clearing, transfer locks, owned-profile creation, failed activation rollback, retry after deletion, and respecting user-selected connections. `npm test` runs frontend tests; build the frontend before `cargo test --locked --manifest-path src-tauri/Cargo.toml --lib`.

Version 0.5.0 local validation passed 61 Rust tests and 83 JavaScript tests, production frontend bundling, fresh Linux DEB/Android debug APK builds, and Windows native-code cross-compilation. New cases cover Windows band selection/fallback, partial-configuration rollback, permission errors, delayed cleanup, preserving system settings, and decoding the actual displayed Windows connection QR without advertising the uplink address. The shared UI tests exercise discovery and joining on each of Android, Linux, Windows and macOS, scan permission failures, timeouts, and sharing an external hotspot without claiming or stopping it. Windows native Rust bindings also pass a Windows-target cross-compilation check. Native Linux WebView tests use an isolated NetworkManager simulator with real local HTTP transfers to exercise the UI/backend boundary without switching the workstation's network. They verify failed activation rollback, previous-network restoration, preservation of a manual network change, clean stop, receiver startup, partial-file cleanup, exact-byte retry and responsive layouts at 360/375/820/1120 px and narrow landscape. A two-app test generates the receiver’s actual QR, feeds it through the production camera workflow using synthetic frames, confirms no network switch before Connect, fills all Wi-Fi/pairing fields, sends exact bytes through the real HTTP receiver, disconnects/restores its connection, and decodes a real QR image through import. QR unit tests cover Unicode/escaping, invalid payloads, actual generated pixel decoding and camera cleanup. This validates workflow integration and profile syntax, not physical radios, cameras or permission dialogs. macOS native code must be compiled on the existing macOS CI runner, which also checks the bundled privacy strings. Windows/macOS runtime behavior and real Android scanning still require device testing:

1. Install the updated APK and desktop build on both devices. Keep both apps visible. Turn off mobile data and disconnect from any router; keep Wi-Fi enabled.
2. Make Android the receiver; create its hotspot. On the other device choose **Scan QR**, point its camera at the receiver, confirm the Wi-Fi name and press **Connect**. Verify that Wi-Fi and pairing fields are filled without typing. Transfer a small file and compare its saved bytes or SHA-256 hash. Repeat through **Choose QR image** and through manual selection in the nearby Wi-Fi list.
3. Send a larger file and several queued files. Check live progress on both devices. Cancel once from the sender and once from the receiver; no partial file should appear in the finished Inbox, later queued files should stop, and an immediate retry should work.
4. Make a supported Linux PC the receiver and repeat from Android. Verify that **Refresh Wi-Fi** requests precise Location and lists the receiver, that denial still permits QR joining, and that the rear camera scans the PC’s QR. Verify the Android system join prompt and transfer with mobile data both enabled and disabled. Stop/disconnect and confirm normal Wi-Fi works afterward. Also test Android-to-Android.
5. Deny permission, reject the join dialog, use a wrong Wi-Fi password, stop a pending setup, turn off the hotspot mid-transfer, and reconnect. Check inline errors, cleanup, and a successful subsequent retry.
6. On Linux, stop its hotspot and confirm the previous connection is restored. Switch networks manually while it is hosting; PulseDrop should clear the old hotspot state without replacing that new connection.
7. Repeat the original **Local network** transfer in both directions after leaving hotspot mode. Test narrow portrait and landscape windows, keyboard operation, and system text scaling on the phone.
8. Build Windows/macOS using GitHub CI. On Windows test native 5 GHz hosting, unsupported-band fallback, an already enabled system hotspot, failure cleanup, saved configuration restoration and preservation of a manual settings change. With native hosting unavailable, test the system-settings fallback. On macOS test joining only for the new 5 GHz workflow. On physical machines, test their nearby Wi-Fi list, QR scan/import, permission denial/retry, joining an offline Android/Linux hotspot, transfer, Disconnect/restoration, and a manual network switch. On macOS use the packaged app so its privacy purpose strings are present. If system hotspot hosting is supported, enable it in Settings, share its credentials through **Share a system hotspot by QR**, receive a file from Android, then hide the QR and confirm the system hotspot remains enabled.

Do not mark hardware testing complete based only on simulated NetworkManager tests or a successful APK build.
